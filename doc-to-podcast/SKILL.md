# Doc to Podcast — 文档转双人对话播客

将任意技术文档/学习笔记转化为**双人对话播客**，输出播客脚本（Markdown）和音频文件（MP3）。

整个流程分两步：先生成播客脚本，再调用 edge-tts 生成音频。两步之间可以由用户审阅修改脚本。

---

## 什么时候用这个 Skill

- 用户想把一篇文档变成"可以听"的版本
- 用户要求生成播客、对话讲解、朗读版
- 用户说"用两个人对话的形式讲一下这个文档"
- 用户给了一个 Markdown 文件，要求转成音频

---

## 第一步：分析源文档

阅读用户指定的源文档，提取以下信息：

1. **主题和目标**：文档讲什么？目标读者是谁？
2. **知识点列表**：按顺序列出所有核心知识点（公式、概念、流程）
3. **类比和例子**：文档中已有的类比，以及可以补充的新类比
4. **文档结构**：有几个大段/章节？每段的核心论点是什么？
5. **风格判断**：是严肃学术论文？还是轻松学习笔记？根据风格决定播客的基调

不需要输出分析结果给用户，这是内部思考步骤。但要在心里形成清晰的"知识点清单"，确保播客脚本覆盖所有要点。

---

## 第二步：设定播客角色

每个播客需要两个角色：

### 角色设定（默认）

| 角色 | 定位 | 说话风格 |
|------|------|----------|
| 🧔 **讲解者**（默认名：小明） | 技术扎实，负责讲解原理 | 清晰、有条理、善用类比 |
| 👩 **提问者**（默认名：小雪） | 新人视角，代表听众 | 好奇、爱追问、善于总结 |

### 角色命名

- 中文文档默认用「小明」+「小雪」
- 英文文档默认用「Alex」+「Sam」
- 用户可以自定义名字

### 角色互动模式

- **提问者**负责：引出话题、要求解释、要求类比、质疑理解、做小结
- **讲解者**负责：技术讲解、给出类比、回答问题、提供数字/公式
- 两人交替发言，形成自然对话节奏
- 每个知识点至少经过"引出→讲解→提问/追问→总结"的循环

---

## 第三步：生成播客脚本

### 脚本格式

严格遵守以下 Markdown 格式，因为后续 TTS 脚本依赖这个格式解析：

```markdown
# 播客标题

> **主播**：
> - 🧔 **小明**（男）— 角色描述
> - 👩 **小雪**（女）— 角色描述

---

## 🎵 开场

**小雪**：开场白，介绍今天的主题～

**小明**：回应，补充背景。

---

## 🎵 第 N 段：段落标题

**小雪**：提问或引出话题。

**小明**：讲解核心知识点，用类比。

**小雪**：追问或确认理解。

**小明**：进一步解释，给数字例子。

---

## 🎵 结尾

**小雪**：总结今天学了什么。

**小明**：结束语，预告下期。

（注意：结尾不要加任何无意义的寒暄或 filler words）
```

### 格式规则（TTS 解析依赖）

1. 每句对话**必须**以 `**名字**：` 或 `**名字**:` 开头
2. 每句对话占**一行**，不要换行
3. 用 `## 🎵` 作为段落分隔符（TTS 会在这里插入停顿）
4. 不要在对话中嵌套代码块、表格、公式——它们不会被朗读
5. 公式要转化为**口语化的文字描述**（例：`Δθ ≈ 2/Nrx` → "角度分辨率大约等于 2 除以天线数"）
6. 代码片段要转化为**文字讲解**（例：`np.fft.fft(x)` → "对 x 做快速傅里叶变换"）

### 脚本质量要求

**自然度**：
- 对话要像真人聊天，不要像念稿子
- 适当用语气词（"嗯"、"哦"、"对"、"没错"），但不要过度
- 提问者偶尔可以说"等等"、"我有个疑问"，打断讲解节奏

**技术准确性**：
- 所有技术点必须来自原文，不要编造
- 公式要完整保留，用口语化方式解释
- 数字和参数要准确，不要四舍五入到离谱

**结构**：
- 开场（30 秒级别）：介绍主题，建立场景
- 主体段落（每段 5-8 分钟级别）：按原文结构，一个知识点一段
- 结尾（1 分钟级别）：总结要点，自测互动

**覆盖度**：
- 源文档的每个主要知识点都必须在播客中提到
- 如果文档有"自测题"部分，在结尾做互动问答
- 如果文档有"代码实践"部分，用文字讲解代码逻辑

### 关于长文档

如果源文档超过 1500 行，播客脚本可能很长。此时：
- 优先覆盖核心知识点，次要细节可以略过但要在对话中提及"这个细节我们就不展开了"
- 将段落控制在 8-10 个以内
- 预估时长超过 45 分钟的，建议用户分拆成多期

---

## 第四步：生成音频

播客脚本写好后，询问用户是否要直接生成音频。

### 前置条件

- 需要 `edge-tts` 库（`uv add edge-tts` 或 `pip install edge-tts`）
- 脚本在 `scripts/generate_audio.py`

### 运行命令

```bash
uv run python <skill-path>/scripts/generate_audio.py <播客脚本.md> <输出.mp3>
```

可选参数：
- `--male-voice` / `--female-voice`：自定义 TTS 声音
- `--male-name` / `--female-name`：指定脚本中男女角色名字

### 中文默认声音

| 性别 | 声音名 | 特点 |
|------|--------|------|
| 男 | zh-CN-YunjianNeural | 稳重，适合讲解 |
| 女 | zh-CN-XiaoxiaoNeural | 自然，适合问答 |

### 可用声音查询

```bash
uv run python -c "
import asyncio, edge_tts
async def main():
    voices = await edge_tts.list_voices()
    zh = [v for v in voices if v['Locale'].startswith('zh-CN')]
    for v in zh:
        print(f\"{v['ShortName']:30s} {v['Gender']}\")
asyncio.run(main())
"
```

### 生成过程

1. 脚本自动解析 Markdown 中的 `**名字**：对话` 格式
2. 根据角色名字自动分配男声/女声
3. 逐段串行生成（带重试），避免服务器限流
4. 拼接所有片段为最终 MP3
5. 194 个片段大约需要 5-8 分钟

### 输出

- MP3 文件，大小约为每分钟 0.3-0.5 MB
- 30 分钟播客约 7-15 MB

## 交互流程

```
用户提供源文档
      │
      ▼
  ① 分析文档结构（内部思考，不输出）
      │
      ▼
  ② 生成播客脚本 Markdown
      │
      ▼
  ③ 展示脚本给用户审阅
      │
      ▼
  ④ 用户确认/修改后，询问是否生成音频
      │
      ▼
  ⑤ 调用 generate_audio.py 生成 MP3
      │
      ▼
  ⑥ 告知用户输出文件位置和大小
```

### 第 ③ 步的呈现方式

展示脚本时，简要说明：
- 预估时长
- 覆盖了哪些知识点
- 段落数量

示例：
> 播客脚本写好了！
> - 预估时长：约 40-50 分钟
> - 覆盖知识点：6 个核心主题
> - 段落：8 段（开场 + 6 主题 + 结尾）
>
> 文件已保存到 `<path>`，你可以先看看有没有要调整的。

---

## 注意事项

- 公式和代码在音频中无法直接呈现，必须转化为口语描述
- 表格内容要转化为对话中的逐条列举
- 图片/图表要在对话中用文字描述其内容
- 技术术语保留英文原文，不需要翻译成中文（"FFT" 就说 FFT，不说"快速傅里叶变换"每次都翻译）
- 每段对话控制在 1-3 句话，太长的句子 TTS 朗读效果不好
