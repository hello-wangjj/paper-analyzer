# Doc to Podcast — 文档转双人对话播客

将任意技术文档/学习笔记转化为**双人对话播客**，输出播客脚本（Markdown）和音频文件（MP3 或 WAV）。

整个流程分两步：先生成播客脚本，再调用 TTS 引擎生成音频。两步之间可以由用户审阅修改脚本。

支持两种 TTS 后端：**Edge TTS**（免费，MP3）和 **MiMo TTS**（自然有感情，WAV）。

---

## 什么时候用这个 Skill

- 用户想把一篇文档变成"可以听"的版本
- 用户要求生成播客、对话讲解、朗读版
- 用户说"用两个人对话的形式讲一下这个文档"
- 用户给了一个 Markdown 文件，要求转成音频

## 第零步：文档类型识别与自适应

> **这是生成高质量播客的前提。** 不同类型的文档需要完全不同的叙事策略。

在深入阅读之前，先判断文档属于以下哪一类，这将决定后续的角色设定和对话风格：

### 文档四分类

| 类型 | 特征 | 推荐模式 | 角色关系 |
|------|------|----------|----------|
| 📚 **教程/指南** | 步骤化结构、"你将会学到"、有代码示例 | 👨‍🏫 师徒模式 | 导师带新手，循循善诱 |
| 📄 **学术论文** | 摘要/引言/方法/实验结构、公式密集、引用多 | 🔍 批判讨论 | 同行讨论，讲解+质疑 |
| 📝 **学习笔记** | 个人化风格、重点标记、有感悟和总结 | 💬 复习对谈 | 两人一起回顾，互为补充 |
| 📊 **技术报告** | 数据密集、有图表、有结论和建议 | 🎤 记者访谈 | 提问者层层追问"为什么" |

### 叙事模式详解

**👨‍🏫 师徒模式（教程/指南类）**
- 讲解者是"老手"，提问者是"第一次接触这个主题的新人"
- 对话节奏：先展示效果 → 倒推原理 → 手把手演练
- 提问者说："这个我好像懂了，但如果是...怎么办？"

**🔍 批判讨论模式（学术论文类）**
- 两人都是懂行的，但提问者偏质疑视角
- 对话节奏：先讲方法 → 质疑假设 → 讨论局限性
- 提问者说："等等，这个假设在实际中成立吗？""如果换成...会怎样？"

**💬 复习对谈模式（学习笔记类）**
- 两人共同学习过，现在一起回顾
- 对话节奏：一个人提起话题 → 另一个人复述理解 → 互相纠正补充
- 提问者说："我记得这里还有个坑..." "不对，这里应该是..."

**🎤 记者访谈模式（技术报告类）**
- 讲解者是项目负责人，提问者是好奇的技术记者
- 对话节奏：提问者引出背景 → 讲解者给出数据和结论 → 提问者追问"所以这意味着什么？"
- 提问者说："这个数字看起来有点反直觉，能解释一下吗？"

### 文档类型确认

分析完文档后，在生成脚本前向用户确认：

> 我判断这份文档是 **[类型]**，推荐使用 **[模式名]**。
> 角色将是 **[讲解者角色定位]** + **[提问者角色定位]**。
> 这样可以吗？要不要调整？

## 第一步：深度分析源文档

> **内部思考步骤，不输出给用户。** 使用以下四步框架深度理解文档。

### A. 内容地图构建

将文档内容分为三个层次：

```
┌─ 主干知识（必须覆盖）─────────────┐
│  核心概念、关键公式、主要结论       │
│  → 播客中至少各出现 1 次            │
├─ 分支知识（选择性覆盖）─────────────┤
│  推导过程、辅助例子、背景补充       │
│  → 选取最有价值的 2-3 个深入讲解    │
├─ 细节层（可略过）───────────────────┤
│  参数微调、边界 case、引用文献       │
│  → 对话中提到"细节不展开"即可       │
└────────────────────────────────────┘
```

**构建方法**：
1. 快速扫读所有标题，形成结构树
2. 标注每个章节的"如果跳过它，后续会看不懂吗？"
3. 依赖关系强的 → 主干；可独立理解的 → 分支

### B. 知识依赖图

识别前置知识关系：
- 概念 A 是理解概念 B 的前提 → A 必须在 B 之前讲
- 概念 C 和 D 是并列的 → 可以按任意顺序
- 概念 E 在文中多次出现 → 第一次出现时详讲，后续只提

### C. 核心概念卡片

为每个核心概念创建一张"卡片"：

```
概念名: 角度分辨率
难度: ★★★★☆
一句话解释: 雷达区分两个相邻目标的最小角度
需要前置知识: 天线阵列、波束形成
最佳类比方向: 人眼的视力表测试
公式: Δθ ≈ 2/Nrx
公式口语化: "角度分辨率大约等于 2 除以接收天线数"
易混淆点: 不是距离分辨率——那是另一个东西
工程意义: 决定雷达能不能分清并排行驶的两辆车
```

### D. 类比匹配

为每个核心概念准备 1-2 个类比：
- **日常类比**（优先）：用生活经验解释
  - 好："角度分辨率就像你的视力——视力越好，越能分辨远处的两个点"
  - 差："角度分辨率就是...呃...天线阵列的一个特性"
- **技术类比**（备选）：用同领域已知概念解释
- **反例**（增强）：说一个常见误解，然后纠正
- **铁律**：原文档中已有的类比**必须保留**，可以在播客中用同样的方式说出来。原文类比是作者精心设计的，不要丢弃。

### E. 知识点清单与关键展开点

> **这是防止内容遗漏的核心步骤。** 生成脚本前，必须先列出完整的知识点清单。

**步骤 1：逐章提取知识点**

为文档的每个章节/任务，列出所有独立的知识点。每个知识点用一行概括：

```
任务2-角度分辨率:
  2.1 公式 Δθ ≈ 2/N（d=λ/2 时）
  2.2 数值例子: N=4→28.6°, N=8→14.3°, N=16→7.2°, N=192→0.6°
  2.3 三个影响因素: 天线数量、天线间距、目标角度
  2.4 cos(θ) 项: 正前方最好，两侧变差
  2.5 栅瓣/空间混叠: d > λ/2 时出现
  2.6 相机像素类比
  ...
```

**步骤 2：标记"关键展开点"**

对每个知识点，识别是否有以下内容需要在播客中展开：

| 类型 | 识别标志 | 处理方式 |
|------|---------|---------|
| 🔢 **数值例子** | 文档中给出了具体数字计算 | **必须保留**，用口语说出数字 |
| 🎯 **原文类比** | 文档中用了"类比"、"就像"、"想象" | **必须保留**，用同样的类比 |
| 📊 **对比数据** | 文档中有表格、多个数值对比 | **必须保留**，逐条列举 |
| 🔗 **物理论证** | 文档解释了"为什么"的推理链 | **必须保留**，不能只给结论 |

**步骤 3：生成覆盖清单**

最终清单格式（内部使用，不输出给用户）：

```
知识点清单（EP01）:
  ✅ 2.1 角度分辨率公式 → 已覆盖
  ✅ 2.2 数值例子 4→28.6° 等 → 🔢 关键展开点，必须保留
  ❌ 2.4 cos(θ) 详细数值 → 🔢 关键展开点，未覆盖！需补
  ✅ 2.6 相机像素类比 → 🎯 原文类比，已保留
```

## 第二步：设定播客角色

### 基础角色模板

每个播客需要两个角色，根据第零步选择的叙事模式选择对应的角色定位：

| 模式 | 讲解者定位 | 提问者定位 |
|------|-----------|-----------|
| 👨‍🏫 师徒 | 经验丰富的导师，耐心、善用类比 | 聪明但缺乏经验的新人，会追问和举一反三 |
| 🔍 批判讨论 | 主讲人，技术扎实 | 同行质疑者，思维敏锐，会挑战假设 |
| 💬 复习对谈 | 回忆者 A，偏理论方向 | 回忆者 B，偏实践方向 |
| 🎤 记者访谈 | 项目负责人/作者，权威但坦诚 | 技术记者，好奇、善于总结 |

### 角色命名

- 中文文档默认用「小明」（男，讲解者）+「小雪」（女，提问者）
- 英文文档默认用「Alex」（男，讲解者）+「Sam」（女，提问者）
- 用户可以在生成脚本前自定义

### 角色互动模式

- **提问者**负责：引出话题、要求解释、要求类比、质疑理解、做小结、打断过长讲解
- **讲解者**负责：技术讲解、给出类比、回答问题、提供数字/公式、确认对方的理解
- **铁律**：同一个人不能连续说 4 句以上（除非在做一个完整的类比说明，但之后必须被打断）
- 每个知识点至少经过"引出→讲解→追问→确认"的循环

## 第三步：生成播客脚本

### 段落设计方法论

每个知识段落使用**三段式结构**：

```
┌─ 具象引入（提问者主导）────────────────┐
│  从日常场景、直观感受、具体数字出发      │
│  目标：让听众"看"到问题                 │
│  时长：约 10%                           │
├─ 抽象讲解（讲解者主导）─────────────────┤
│  讲原理、给类比、拆公式、举例子          │
│  目标：建立知识框架                      │
│  时长：约 60%                           │
├─ 具象验证（提问者追问）─────────────────┤
│  举一反三、确认理解、连接实际应用        │
│  目标：巩固和延伸                        │
│  时长：约 30%                           │
└─────────────────────────────────────────┘
```

**反例**（避免这样做）：
```
❌ "你好，今天我们来学习角度分辨率。角度分辨率定义为雷达能区分两个目标的最小角度差..."
   → 上来就抛定义，听众没建立直觉就晕了
✅ "小雪：小明，我一直好奇，雷达是怎么分清楚并排跑的两辆车的？
    小明：好问题！这靠的是'角度分辨率'。你可以把它想象成测视力...E 字开口太小你就分不清了。
    小雪：哦！所以角度分辨率就是雷达的'视力'？
    小明：对。具体来说，它等于 2 除以天线数..."
```

### 对话节奏控制

- **长讲解阻断**：讲解者连续说了 2-3 句后，提问者必须插入（"等等，我确认一下..."）
- **总结锚点**：每 5-6 轮对话后，有一轮专门的总结（提问者："所以总结一下，我们刚才学了..."）
- **难度攀升**：开头最易懂的概念 → 逐步加深 → 结尾回到全局视角
- **兴奋曲线**：每隔 2-3 段有一个"恍然大悟"时刻或有趣的类比

### 对话深度扩展

> **核心原则：每个知识点不能一笔带过，必须经过多轮追问展开。**

**展开模式**：每个核心知识点至少经历 5 轮对话：

```
第1轮 提问者引出话题："这个东西是干什么的？"
第2轮 讲解者给直觉解释 + 类比
第3轮 提问者追问："能举个具体数字吗？" / "为什么是这样？"
第4轮 讲解者给数值例子 / 物理推导
第5轮 提问者确认理解："所以就是说..." / 连接到下一个话题
```

**提问者的追问模式**（每段至少用 2-3 种）：

| 追问类型 | 示例 |
|----------|------|
| 要求数字 | "能算个具体数字感受一下吗？" |
| 要求类比 | "能打个比方吗？用生活中的例子。" |
| 要求解释原因 | "为什么是这样？背后有什么道理？" |
| 确认理解 | "所以你的意思是...对吧？" |
| 质疑/反例 | "但如果条件变了呢？比如..." |
| 连接已知 | "这个跟前面讲的XX有什么关系？" |
| 要求对比 | "跟另一种方法比呢？优劣是什么？" |

**每行对话长度**：约 40-80 字（1-3 个短句）。太短则信息密度低，太长则 TTS 朗读吃力。时长换算见第四步"时长估算规则"。

**反例**（太短，信息密度低）：
```
❌ 小雪：角度分辨率怎么算？
   小明：约2除以天线数。
   小雪：哦明白了。
→ 3 句话只传递了一个公式，没有数字、没有类比、没有追问
```

**正例**（展开后）：
```
✅ 小雪：角度分辨率怎么算？能给个公式吗？
   小明：角度分辨率大约等于2除以天线数，单位是弧度。完整公式里还有一项余弦因子，但先记住简化版就够用了。
   小雪：给我几个具体数字感受一下。
   小明：4根天线大约28.6度，8根14.3度，16根7.2度，到192根就只有0.6度了。
   小雪：28度也太粗了吧？那4根天线基本只能分左右。
   小明：对，传统4天线雷达就这水平。要想分车道，至少得上MIMO，12个虚拟天线大约9.6度。
   小雪：打个比方的话，天线数量就像相机像素？
   小明：完全正确。4个天线就像4像素的照片，拍出来一团模糊。192个天线就像高清照片，细节纤毫毕现。
→ 8 句话，有公式、有数字、有类比、有追问、有确认
```

### 段落桥接

每段结尾必须有连接到下一段的过渡句，不能突然跳跃。方式包括：
- 提问者："那这个东西在实际中怎么用呢？"（自然引出应用段落）
- 讲解者："说到这个，就不得不提另一个相关概念..."（自然引出相关概念）
- 提问者："不过我有个疑问，如果条件变了呢？"（引出限定条件和局限性）

### 脚本格式

严格遵守以下 Markdown 格式，因为后续 TTS 脚本依赖这个格式解析：

```markdown
# 播客标题

> **主播**：
> - 🧔 **小明**（男）— 角色描述
> - 👩 **小雪**（女）— 角色描述

---

## 🎵 开场

**小雪**：开场白，介绍今天的主题～（不要用"大家好，欢迎来到..."这种播音腔）

**小明**：回应，补充背景。建立场景感。

---

## 🎵 第 N 段：具象的段落标题

**小雪**：从场景/问题出发引出话题。

**小明**：讲解核心知识点，用类比建立直觉。

**小雪**：追问或确认理解。

**小明**：深入讲解，给数字/公式/例子。

**小雪**：总结这一段的核心收获，并自然过渡到下一段。

---

## 🎵 结尾

**小雪**：用"如果只记住三件事"的方式总结。

**小明**：补充最重要的一个 insight，结束。

（注意：结尾不要加任何无意义的寒暄例如"那今天就到这里，下期再见"，也不要加 filler words）
```

### 格式规则（TTS 解析依赖）

1. 每句对话**必须**以 `**名字**：` 或 `**名字**:` 开头
2. 每句对话占**一行**，不要换行
3. 用 `## 🎵` 作为段落分隔符（TTS 会在这里插入停顿）
4. 不要在对话中嵌套代码块、表格——它们不会被朗读
5. 段落标题要**具象**，例如：
   - ✅ `## 🎵 雷达的"视力"：角度分辨率是什么`
   - ❌ `## 🎵 第二节 角度分辨率的概念`

> 完整的格式与质量参考样例见 [`assets/example_episode.md`](assets/example_episode.md)——它同时是格式锚点（怎么写才符合 TTS 解析）和质量锚点（数值保真、追问展开、结尾收 insight）。

### 非文本内容转化方法论

#### 公式转化四步法

对每个核心公式，按以下四步转化为对话：

```
1. 直觉层：这个公式告诉我们什么？（一句话概括物理含义）
   → "这个公式告诉我们，天线越多，雷达看得越清楚。"
   
2. 拆解层：逐项解释每个符号的含义
   → "分子上的 2 是一个常数，分母 N 是天线数量..."
   
3. 极端层：给极端情况帮助理解
   → "如果只有 1 根天线，分辨率就是 2 弧度——基本等于瞎了。但如果有 100 根天线..."

4. 工程层：这在工程上意味着什么？
   → "所以你要想提升角分辨率，加天线比改进算法有效得多。"
```

在对话中，这四个层次分布在提问者和讲解者之间，形成自然的互动。

#### 代码转化：执行过程叙述法

不逐行读代码。而是描述：
1. **这段代码要解决什么问题？**
2. **它的大致逻辑是什么？**（先做什么、再做什么、最后输出什么）
3. **关键的 trick 或容易出错的地方**

示例转化：
```python
# 原文代码（不会一字一句读）
range_fft = np.fft.fft(adc_data, axis=0)
range_fft = np.fft.fftshift(range_fft)
```

→ 对话中的表述：
> **小明**：首先对 ADC 采集的原始数据按列做 FFT，相当于把时域的回波信号转换到频域——因为不同频率对应不同距离嘛。然后做 fftshift 把零频移到中间，这样距离谱就从"负距离到正距离"变成了我们习惯的"从近到远"的排列。

#### 图表转化：空间描述法

1. 先描述整体：横轴是什么、纵轴是什么、有几条曲线
2. 指关键数据点：最大值在哪、转折点在哪
3. 给结论：这张图的核心信息是什么

对话中表述：
> **小雪**：我看到论文里有个图，横轴是 SNR，纵轴是检测概率，有三条曲线分别对应不同的算法。我们的方法在低 SNR 下明显比其他两条曲线高——这是最关键的结论对吧？

#### 表格转化：逐条对比法

表格数据变成对话中的逐条列举。示例：
> **小明**：对比一下，方法 A 用了 256 个天线，角度分辨率 0.5 度；方法 B 只用 64 个天线，但用了超分辨率算法，分辨率反而做到了 0.3 度——核心差异就在这。

### 内容保真规则

> **生成脚本时，以下内容必须从原文保留到播客对话中，不能省略。**

#### 规则 1：数值例子必须保留

原文中所有给出**具体数字**的例子，播客中必须用口语说出来：

```
原文: "θ=30° 时，导向矢量 a(30°) = [1, j, -1, -j]ᵀ"
  
  ❌ 播客中省略: "不同角度的导向矢量不一样"
  ✅ 播客中保留: "比如目标在三十度方向，四个天线的信号分别是 1、j、负 1、负 j，
                  相当于信号在天线之间逐个旋转九十度"
```

**识别方法**：原文中有 `=` 号后面跟具体数字/向量的，都是数值例子。

#### 规则 2：原文类比必须保留

原文作者精心设计的类比，播客中必须使用（可以用自己的话重新组织，但核心比喻不能丢）：

```
原文: "想象你在火车上：窗口1看到的景象 = A，窗口2看到的景象 = A 平移了一点 = A × Φ"
  
  ❌ 播客中省略: 只说"ESPRIT 利用平移不变性"
  ✅ 播客中保留: "想象你在火车上，从第一个窗口看出去是景象 A，
                  从第二个窗口看出去是 A 平移了一点——这个平移量就编码了方向"
```

**识别方法**：原文中有"想象"、"就像"、"类比"、"比方"等词的段落。

#### 规则 3：对比数据必须保留

原文中的表格和多组数值对比，播客中必须逐条列举：

```
原文表格:
  Nrx=4  → 28.6°
  Nrx=8  → 14.3°
  Nrx=16 → 7.2°
  Nrx=192→ 0.6°

  ❌ 播客中省略: "天线越多分辨率越高"
  ✅ 播客中保留: "四个天线二十八度，八个十四度，十六个七度，一百九十二个零点六度"
```

#### 规则 4：物理论证链必须保留

原文中解释"为什么"的推理链，播客中不能只给结论，必须保留推理过程：

```
原文: "虚拟天线能当真的用，因为12个虚拟天线的空间位置和12个真实天线完全一样，
       每个位置的天线收到的信号相位完全相同"
  
  ❌ 播客中省略: "虚拟天线效果和真实天线一样"
  ✅ 播客中保留: "关键在于，十二个虚拟天线排在的位置，跟十二个真实天线排在的位置
                  完全一样。每个位置收到的信号相位也完全一样，所以角度估计的效果相同"
```

## 第四步：脚本自检

脚本写完后，**先做内容覆盖度验证，再做格式自检**。两项都必须通过。

### A. 内容覆盖度验证（最重要）

> **拿着第一步 E 节生成的知识点清单，逐条核对脚本。**

核对方法：对清单中的每个知识点，在脚本中搜索是否有对应的对话。

```
核对示例:

知识点 2.1 角度分辨率公式 → 搜索"分辨率" → 找到小明说"角度分辨率大约等于二除以天线数" → ✅
知识点 2.2 数值例子 N=4→28.6° → 搜索"二十八" → 找到小明说"二十八点六度" → ✅
知识点 2.4 cos(θ) 详细数值 → 搜索"cos"/"余弦"/"两侧" → 只有"越往两侧越差"，无数值 → ⚠️ 部分覆盖
知识点 4.16 火车窗口类比 → 搜索"火车"/"窗口" → 未找到 → ❌ 未覆盖
```

**对未覆盖/部分覆盖的处理**：

- 关键展开点（🔢 数值 / 🎯 类比 / 📊 对比 / 🔗 论证）未覆盖 → **必须补入**，具体转化方法见第三步"内容保真规则"。
- 📝 普通知识点未覆盖 → 评估重要性：主干必补，分支可略。

**目标**：主干知识 100% 覆盖，关键展开点 100% 覆盖。

### B. 格式自检清单

| # | 检查项 | 不通过的表现 |
|---|--------|-------------|
| 1 | 所有公式/代码/图表都转化为口语描述？ | 对话中出现了 `np.fft()` 或 Δθ 等原始符号 |
| 2 | 每个段落以"具象引入"开头，而非直接抛概念？ | 第一句就是"XX 的定义是..." |
| 3 | 提问者的知识水平前后一致？（不会突然变成专家） | 提问者上一句还在问基础问题，下一句就讲起了推导 |
| 4 | 没有连续 4 句以上同一个人说话？ | 讲解者一大段独白 |
| 5 | 结尾没有无意义寒暄？（"今天就到这里""下期再见"等） | 结尾出现空洞的结束语 |

### 长文档多期拆分策略

当预估时长超过 20 分钟时，必须将文档拆分为多期播客。**每期严格控制在 20 分钟以内。**

#### 时长估算规则

中文 TTS 语速约 150 字/分钟。以下口径互相自洽，按这个来，不要再记别的数字：

- **每个知识段落**（5-8 行对话）≈ **2-3 分钟**
- 开场 ≈ 1 分钟，结尾 ≈ 1 分钟
- **20 分钟 ≈ 6-8 个知识段落**（含开场和结尾）≈ 40-60 行对话
- 单期预估超过 8 个段落 → 判定超时，必须按"长文档多期拆分"处理

> 校验：6 段 × 2.5 分钟 + 开场结尾各 1 分钟 ≈ 17 分钟，落在 20 分钟内。✓

完整的拆分方法论（拆分原则、每期结构、首尾衔接钩子、文件命名、生成流程、分集大纲模板）在 [`references/multi-episode.md`](references/multi-episode.md)。

**长文档处理流程**：预估超时 → 先读 `references/multi-episode.md` → 生成分集规划 → 逐期生成脚本（每期独立文件）→ 逐期自检。

## 第五步：生成音频

播客脚本写好后，询问用户是否要直接生成音频。

### 两种 TTS 后端

| 对比 | Edge TTS | MiMo TTS |
|------|----------|----------|
| 音质 | 清晰，偏机械 | 自然有感情，支持风格控制 |
| 费用 | 免费 | 限时免费 |
| 输出格式 | MP3 | WAV（无损） |
| 认证 | 无需 key | 需 `MIMO_API_KEY` 环境变量 |
| 默认男声 | zh-CN-YunjianNeural | 白桦（深沉磁性） |
| 默认女声 | zh-CN-XiaoxiaoNeural | 冰糖（清亮甜美） |
| 音频标签 | 不支持 | 支持（兴奋、疑惑、恍然大悟等） |

### 运行命令

脚本在 `scripts/generate_audio.py`，通过 `--backend` 参数选择后端：

```bash
# Edge TTS（默认，免费无需 key）
uv run python <skill-path>/scripts/generate_audio.py <播客脚本.md> <输出.mp3>

# MiMo TTS（自然有感情，需要 API key）
$env:MIMO_API_KEY="your-key"   # PowerShell
export MIMO_API_KEY="your-key" # Bash
uv run python <skill-path>/scripts/generate_audio.py <播客脚本.md> <输出.wav> --backend mimo

# 可传入文档主题帮助 MiMo 生成更适合的风格（可选）
uv run python ... --backend mimo --topic "多目标跟踪雷达技术"
```

可选参数：
- `--backend edge|mimo`：选择 TTS 后端（默认 edge）
- `--topic`：文档主题，帮助 MiMo 生成更贴合内容的语音风格（默认"技术知识"）
- `--male-voice` / `--female-voice`：自定义 TTS 声音
- `--male-name` / `--female-name`：指定脚本中男女角色名字
- `--no-tags`：禁用自动音频标签（MiMo only）

### Edge TTS 可用声音

| 性别 | 声音名 | 特点 |
|------|--------|------|
| 男 | zh-CN-YunjianNeural | 稳重，适合讲解 |
| 男 | zh-CN-YunxiNeural | 自然 |
| 女 | zh-CN-XiaoxiaoNeural | 自然，适合问答 |
| 女 | zh-CN-XiaoyiNeural | 活泼 |

### MiMo TTS 预置声音

| 性别 | 声音名 | 特点 |
|------|--------|------|
| 男 | 白桦 | 深沉磁性，适合讲解 |
| 男 | 苏打 | 沉稳干练 |
| 女 | 冰糖 | 清亮甜美，适合提问 |
| 女 | 茉莉 | 温柔知性 |

### MiMo 风格控制

MiMo 后端会自动为每段对话添加风格：
- **自然语言控制**：通过 user 消息设定角色性格（讲解者沉稳/提问者活泼），会根据 `--topic` 参数调整内容相关性
- **音频标签**：自动根据文本内容添加情绪标签，如 `(兴奋)` `(疑惑)` `(恍然大悟)` `(轻笑)`

用户可以传 `--no-tags` 禁用自动标签。

### 生成过程

1. 脚本自动解析 Markdown 中的 `**名字**：对话` 格式
2. 根据角色名字自动分配男声/女声
3. 逐段串行生成（带重试），避免服务器限流
4. 拼接所有片段为最终音频
5. 150+ 个片段大约需要 5-10 分钟

### 输出

- Edge TTS: MP3 文件，约每分钟 0.3-0.5 MB
- MiMo TTS: WAV 文件，约每分钟 3-5 MB（无损）

## 注意事项

- 公式和代码在音频中无法直接呈现，必须转化为口语描述
- 表格内容要转化为对话中的逐条列举
- 图片/图表要在对话中用文字描述其内容
- 技术术语保留英文原文，不需要翻译成中文（"FFT" 就说 FFT，不用说"快速傅里叶变换"每次都翻译）
- 每段对话控制在 1-3 句话，太长的句子 TTS 朗读效果不好
- **最重要的一条**：好的播客听起来像两个人在聊天，不是两个人在念稿。多用自然的口语表达。
