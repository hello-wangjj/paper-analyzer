# 四种交接边界：额外要求与检查清单

契约结构（九节）对所有边界相同，差别在于**哪些字段必须更硬**。先按下面的判据确定 `boundary`，再照对应清单补完。

## 边界判定

| 实际情形 | boundary |
|---|---|
| 上下文将满、要开新 session、模型换了但工具没换 | `context-exhaustion` |
| 换客户端（Claude Code ↔ Codex ↔ WorkBuddy ↔ ZCode ↔ kilo ↔ opencode），或换模型档位 | `tool-switch` |
| 交给同事、另一个 agent、专家角色，需要划权限 | `agent-handoff` |
| 任务从仓库 A 迁到仓库 B，或从项目目录迁到另一个项目目录 | `migration` |

同时符合多项时，按**对接收方影响最大**的那一项填。例如"换工具 + 换人"填 `agent-handoff`，但在 §6 按 `tool-switch` 的要求写全。

---

## context-exhaustion：上下文耗尽续接

**核心风险**：时间不够，写成了流水账摘要，产物没交出去。

**优先级**：§3 → §8 → §1 → §4/§5。分析、讨论过程可以砍，产物和下一步不能砍。

### 检查清单

- [ ] §3 里每一个正在改的文件都有路径 + sha + 行号区间
- [ ] 只存在于对话里的草稿、方案、待发消息，已整段粘贴进围栏
- [ ] §8 第一步是"打开哪个文件的哪一段、改成什么"，不是"继续优化"
- [ ] §2 里所有 `[x]` 的验证命令，你能在 5 分钟内重跑一遍
- [ ] §4 列全了本轮已经拍板的结论，包括"不做 X"这种否定决策
- [ ] `head` 与当前分支实际 HEAD 一致；若产物未提交，§7 已注明

### 常见错误

- 把"我们讨论了三种方案"写进 §4。讨论过程不属于锁定决策，只有结论属于。
- §3 写"代码已经改好了"。没有路径和行号，等于没交接。

## tool-switch：换工具或换模型

**核心风险**：记录里混入只有原工具能解释的东西，新工具读到等于噪声。

### 必须额外满足

1. **§6 能从零重建**：从干净机器开始，照表能装出同样的环境。缺一步就等于没写。
2. **禁止客户端私有引用**：会话 id、"上文提到的"、应用内链接、只有某 App 能解析的引用、临时目录路径，全部不允许。
3. **路径必须跨工具可解析**：Windows 下统一正斜杠；盘符路径写全；不要写 `~` 之外的 shell 变量。
4. **不提模型能力假设**：不写"你应该能直接看到文件"，写清文件在哪、用什么命令读。
5. **凭据按名字交接**：不同工具读不到同一份钥匙串。写"变量名 + 由谁提供"，不写"用我之前的配置"。

### 检查清单

- [ ] 全文搜索过"上文""刚才""之前那个""这个文件"，全部换成了具体路径或整段粘贴
- [ ] §6 的每条命令都能在新工具里直接粘贴执行，不依赖原工具的 shell 别名或插件
- [ ] §3 没有指向 `.workbuddy/`、`~/.claude/`、`/tmp` 等客户端私有或临时位置（除非产物确实在那里且写明理由）
- [ ] 记录本身不依赖任何 front matter 之外的元数据（比如"见附件""见任务卡"）
- [ ] 新工具若不支持某个能力（浏览器、图像、长上下文），§7 已写明降级方案

### 常见错误

- 写"接着上次那个改"。新工具没有"上次"。
- §6 只写"需要 Python 3.13"。缺 venv 位置、依赖安装命令、环境变量名。
- 把 sha 写成"最新提交"。时钟一走就失效。

## agent-handoff：换人或换 agent

**核心风险**：权限没划清，接手方改了不该改的；验收标准依赖原交接方的主观判断。

### 必须额外满足

1. **§7 写清决策权**：哪些能自决、哪些必须回来问、谁是最终验收人。
2. **§1 的判据第三方可判**：换一个没参与过的人，照判据能得出同样的"通过/不通过"。
3. **§7 写清禁止触碰**：对外接口、生成代码、他人负责的模块、已冻结的配置。
4. **§4 列出不可重开的决策**，并说明重开的条件（"除非 X 出现"）。
5. **角色定位**：接手方是执行者、评审者还是决策者，一句话写在 §7 开头。

### 检查清单

- [ ] §1 每条判据都能被第三方独立验证，不含"符合预期""合理"这类词
- [ ] §7 有明确的验收人名字或角色
- [ ] §7 的"可修改范围"是路径，不是模块名
- [ ] §5 的否决路径写清了失败现象，避免接手方出于"想试试"重走
- [ ] 若需要评审闸门，§8 的步骤里显式写了"谁评审、评审通过才进入下一步"

### 常见错误

- 只写"你看着办"。授权不清时，接手方要么过度保守（不动），要么越界（乱动）。
- 验收标准写成"我觉得可以了"。这不是判据，是授权模糊。

---

## migration：跨项目或跨仓库迁移

**核心风险**：路径失效、依赖漏迁、外部契约在迁移中被悄悄改掉。

### 必须额外满足

1. **§6 给路径映射表**：源 → 目标，逐条列。目录整体搬家写目录级映射，个别文件单独列。
2. **依赖声明**：目标仓已有的依赖版本是什么；迁移是否要求升级/降级；不兼容点在哪。
3. **外部契约**：数据格式、接口签名、文件名、环境变量名是否随迁改变。**改变必须在 §4 记录并说明兼容策略**，不能不声不响地改。
4. **§3 的引用指向目标仓可访问位置**：源仓路径对目标仓的接手方可能不存在。要么给绝对路径并确认可读，要么先复制过去再引用。
5. **留下什么**：明确源仓里哪些东西不迁、是否删除、是否保留兼容层。删除项写进 §5。
6. **回滚路径**：迁移失败时怎么退回去，写在 §7。

### 检查清单

- [ ] §6 路径映射表覆盖 §3 里出现的每一个路径
- [ ] 目标仓的构建与测试命令已实跑通过，结果写进 §2 的验证
- [ ] 环境变量、配置键、数据文件名若改名，§4 有记录，§7 有兼容或迁移脚本说明
- [ ] 源仓里被删除的文件已在 §5 说明，不留下悬空引用
- [ ] git 历史处理方式已写明（保留 / squash / 不迁），以及 `head` 指哪一边
- [ ] `project_root` 指向目标仓，不是源仓

### 常见错误

- 映射表只写顶层目录，漏掉配置、脚本、测试数据。
- 迁移后 `project_root` 忘了改，§3 的路径校验会全部失败（这也是校验器存在的意义之一）。
- 在目标仓重建代码而不是迁移，然后声称"已迁移"。这属于 §5 的否决路径，不是迁移。

## 多次交接：同一条链上的约束

同一任务第二次及以后的交接：

1. **覆盖同一个文件**，不新建 `-v2`。
2. §9 **追加**一行，不删历史。
3. §4 只增不减。被推翻的决策不删除，改为在 §9 记录"因新证据 X 重开"，并在 §4 更新结论与理由。
4. §5 只增不减。曾经否决的路径即使后来又被采用，也保留原记录并说明为何改判。
5. §2 的 `[x]` 可以累积，但验证命令必须仍然可跑。跑不动了就降回 `[ ]` 并说明。

链条断裂的典型信号：§9 有两行但 §4 的决策在被反复推翻。这说明决策当时没写清理由，或者交接方没有真的锁定。
