# 版本化产出目录规范

## 目标

专利交底书会反复生成、补充技术细节、重新导出 Word。所有用户可见产物必须按版本目录保存，避免在同一层目录堆放大量带时间戳的文件。

## 目录结构

用户给出产出目录时，将其视为**专利组根目录**或**案件根目录**。根目录只保留版本索引、修订日志和版本文件夹：

```text
{专利组或案件根目录}/
├── 版本索引.md
├── 交底书修订对话记录.md
├── v1-初版-20260824120000/
│   ├── {案件名}_{YYYYMMDDHHMMSS}.md
│   ├── {案件名}_{YYYYMMDDHHMMSS}.docx
│   ├── {项目名}_专利簇通俗说明清单_{YYYYMMDDHHMMSS}.md   （多件交付时，见 patent_family_explainer.md）
│   └── mermaid_figures/
└── v2-技术细节增强-20260825100000/
    └── ...
```

若用户指定的是单件专利目录，也使用同样结构；若一次交付多件专利（同一批确认的多个拟申请点），所有同批次文件放入**同一个版本目录**。

## 版本目录命名

版本目录格式：

`vN-简短说明-YYYYMMDDHHMMSS`

规则：

1. `N` 为当前根目录下已有 `v数字-` 目录的最大编号加 1；没有旧版本时从 `v1` 开始。（历史已用简式 `v1/`、`v2/` 命名的，沿用其最大编号递增。）
2. 简短说明用 4-12 个中文字符或短词，例如 `初版`、`技术细节增强`、`补充实施例`、`纠错修订`、`权利要求强化`。
3. 时间戳使用本次交付时间，与主文件名时间戳保持一致。
4. **不覆盖、不删除旧版本目录**；用户明确要求覆盖时，也应先提醒覆盖会破坏版本追溯。旧版本需找回时可从 git 历史 `git checkout <commit> -- <path>` 恢复到对应 `v{N}/` 子文件夹。

## 文件放置规则

- `.md`、`.docx`、专利簇通俗说明清单、mermaid 资源目录（`mermaid_figures/`，含 PNG 与 `.mmd` 源）、用户要求的 `.pdf`，均放在**当前版本目录**。
- 当前版本 Markdown 内的相对图片路径必须指向同版本目录内的资源目录，例如 `mermaid_figures/fig_001.png`。
- **根目录不得新增定稿文件**；根目录只更新 `版本索引.md` 和 `交底书修订对话记录.md`。
- 主文件名仍须为 **`{案件名}_{YYYYMMDDHHmmss}`**（`disclosure_builder.md` §7.3 第 5 点，**含首次定稿与迭代**）。
- 若发现历史产物已经平铺在根目录，后续交付前应整理到 `v1/v2/...` 或至少从新版本开始遵守本规则。

## 版本索引

每次交付或迭代后，必须创建或更新根目录 `版本索引.md`，至少包含：

1. 当前推荐阅读版本。
2. 版本清单表：版本目录、生成时间、内容、阅读建议。
3. 当前版本包含的专利文件、专利簇说明清单、Word 情况。
4. 后续版本规则：新一轮修改创建下一个 `vN-说明-时间戳/`，不覆盖旧版本。

`版本索引.md` 面向用户阅读，语言要直白，让用户一眼知道应该看哪个版本。多版本并存时（如详细版/精简版），在索引中简要说明各版本差异（例：「v1 详细版：15 节点系统框图 + 5 个公式；v2 精简版：7 节点系统框图 + 2 个核心公式」）。

## 迭代时的处理

补材料、纠错、强化权利要求偏向点时：

1. 读取用户指定或 `版本索引.md` 标记的当前推荐版本作为基准。
2. 新建下一个版本目录，例如 `v4-补充实施例-YYYYMMDDHHMMSS/`。
3. 把本轮生成的所有交付文件写入该版本目录。
4. 更新根目录 `版本索引.md`，将当前推荐版本指向新版本。
5. 在根目录 `交底书修订对话记录.md` 追加本轮记录（`tools/iteration_dialog_log.py` 或等价手工）。

## 回复用户时

交付回复中应给出：

- 根目录 `版本索引.md` 路径。
- 当前推荐版本目录。
- 主要 Word / Markdown 文件路径。

不要只给出一串平铺文件名。
