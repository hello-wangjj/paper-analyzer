# 技术交底书生成模板（Step 7，对齐所内 docx 模板）

本技能的交底书结构**严格对齐 `【参考】专利技术交底书模板.docx`**（封面元数据表 + 一~六章）。完整字段、撰写要求与 **mermaid / 公式** 范例见 **`template_reference.md`**。

## 7.1 章节结构（对齐 docx 模板）

```
0. 封面：案件管理信息表（见 template_reference「封面」；敏感字段留 [待填写]）
1. 一、发明/实用新型名称（≤25字，与封面「拟申报专利名称」逐字一致）
2. 二、所属技术领域（具体技术领域/直接应用领域，一句话到一小段）
3. 三、背景技术
   - 3.1 现有技术（技术现状 + 文件出处 + 公开源 URL；含「检索说明」）
   - 3.2 现有技术存在的问题（=本发明创造的灵感来源，≥100字）
   - 3.3 业内克服现有技术缺陷的尝试（同行改进路线 + 文件出处，≥100字）
4. 四、创新点
   - 4.1 要解决的技术问题（对应 3.2 缺点）
   - 4.2 为解决技术问题而采取的技术方案（≥200字，核心）
       · 4.2.1 系统框图（**mermaid**，`flowchart`+`subgraph` 分层；交付前经工具转 PNG；**不要** ASCII 文字框图）
       · 4.2.2 模块功能说明（聚焦作用与关联关系，非输入输出）
       · 4.2.3 系统流程说明（**mermaid 流程图**，交付前经工具转 PNG；**不要** ASCII 文字/箭头流程图）
       · 4.2.4 符号与公式（出现公式或形式化变量时**须设**；**须**先符号与变量定义、再写公式；体例见 **§7.7** 与 **`template_reference.md` §4.2.4**）
       · 4.2.5 关键技术参数（参数表「符号」列与 4.2.4 **同形**）
   - 4.3 本发明技术方案的代替方案（不同构思，有则填写；扩大保护范围）
   - 4.4 本发明解决技术问题的有益效果/进步效果（与 3.2、4.1 闭环）
   - 4.5 本发明技术效果的逻辑论证（≥100字；方案→效果→论证）
5. 五、发明技术方案的具体实施方式（实施例1…，至少一个，建议对应保护方案）
6. 六、发明附图及说明（附图汇总表 + 各图简要说明；发明专利一定要有附图）
```

**第三章 3.1 撰写硬性要求**：在「按技术方向分类」的**每一条**现有技术（专利或文献）末尾或表格中，必须给出 **经核验的公开源 URL**（规范与示例见 `prior_art_search.md` 与 `template_reference.md` §3.1）。**国知局检索**（`EPUB_HITS_JSON`）中对该专利给出的 **`abstract` 非空时**：文中「技术方案 / 应用 / 局限」类表述**须以摘要理解为前提**（消化后重写，非整段粘贴），**禁止**与摘要明显矛盾或脱离摘要杜撰；详见 **`prior_art_search.md`**「`abstract` 必用」。**3.3 业内尝试**同样要求附文件出处与公开 URL，与 3.1 互补（3.1 偏最接近现状、3.3 偏同行改进路线）。

**禁止输出**：交底书正文中**不得**包含「自检清单」章节，例如检查项表格或带状态符号的清单列。自检见 `disclosure_self_check.md`，**内部执行**，不写入交付正文。

**禁止仓库/技能脚注**：交付用 Markdown **末尾不得**出现任何指向本技能或示例仓库的说明，例如「本文件为 `customize-patent-disclosure-skill` 仓库内教学示例」「不构成任何法律或技术承诺」「虚构教学」「详见 `examples/`」等。正文**止于第六章及此前章节**；**不要**在文末追加斜体免责或仓库署名。

**封面表填写纪律**：身份证号、组织机构代码证、委托编号等敏感/流程字段**一律** `[待填写]`，由提案人或知识产权人员手填，**Agent 不得主动编造或猜测**；仅「拟申报专利名称」由本案内容推出后填入，并与第一章名称**逐字一致**。

## 7.3 输出文件命名（用户产出目录，必遵循）

在用户目录（如 `outputs/{案件标识}/`）写入交底书 **Markdown / Word** 时，**主文件名须体现正文中的「案件名称」**，且**凡向用户落盘交付的定稿均须带时间戳后缀**（见下第 5 点），避免无区分度的固定名（如一律 `disclosure_draft.md`）。**仓库内 `examples/` 为教学统一可仍用固定名**；用户产出不适用该惯例。

1. **提取**：从封面表「拟申报专利名称」或第一章名称取完整发明名称；去掉占位（如 `[待填写]`、`【待填写】`）、首尾空格。
2. **规范化**：删除或替换 Windows 非法字符 `\ / : * ? " < > |` 与换行；连续空格可压为单个空格或删去（中文标题通常无空格亦可）。
3. **长度**：文件名（不含扩展名）建议 **≤ 80 个字符**；超长则**截断**到约 80 字并保留语义完整（例如截在「方法及系统」等结尾词之前），勿用无意义随机串。
4. **定稿命令**：`mermaid_render.py` 的 `-o` / `--docx` 须使用**同一主文件名**，且该主名**必须符合第 5 点**（**案件名 + `_` + 14 位时间戳**）。**公式无需单独渲染**——`md_to_docx.py` 内置 LaTeX → OMML 转换器（依赖 `latex2mathml`），公式直接转为 Word 原生公式（可编辑、矢量清晰），不再生成 PNG 图片。示例（案件名已按上文规范化、过长已截断时）：

   `python3 tools/mermaid_render.py -i "…草稿.md" -o "一种异构计算环境下基于资源画像与限频重排队的批任务调度方法及系统_20260408143025.md"`

   默认同目录生成同名 `.docx`。过程性中间稿（仅自用、非交付）文件名可自定，但**最终交付**不得省略时间戳。

5. **时间戳后缀（凡落盘交付必遵循）**：凡写入用户产出目录、作为**向用户交付**的技术交底书 **`.md` / `.docx`**，主文件名须为：  
   **`{§7.3 规范化案件名}_{YYYYMMDDHHmmss}.md`** 与同名 **`.docx`**。  
   - **首次定稿**与**迭代合并/纠正**适用**同一规则**；每次交付取**当次落盘时**的**本地时间** 14 位数字（年月日时分秒各 2 位，如 `20260408143025`）。  
   - **不要覆盖**已有交付文件；新一次交付即**新时间戳**、新文件名。用户**明确要求**覆盖某路径时从其意。  
   - **`mermaid_render.py`** 的 `-o` 与可选 `--docx` 须与上述主名一致。  
   - **例外**：（1）仓库内 **`examples/`** 示例可继续固定文件名；（2）用户书面指定文件名时从其意（仍建议保留时间戳以免混淆）。

6. **版本分文件夹（必遵循，细则见 `prompts/versioned_output.md`）**：用户产出根目录视为**专利组/案件根目录**，交付产物写入 **`vN-简短说明-YYYYMMDDHHMMSS/`** 版本文件夹（如 `v1-初版-20260824120000/`），文件夹内包含**完整自洽产物**：`.md` + `.docx` + `mermaid_figures/`（多件交付时含专利簇清单）。**禁止**把多版本定稿平铺在同一层目录以文件名区分；根目录只维护 **`版本索引.md`** 与 **`交底书修订对话记录.md`**。生成新版本**不得覆盖或删除**旧版本文件夹；交付回复中简要说明各版本差异。

Agent **落盘时**即采用上述命名，并在回复中写明路径，便于用户对照标题与磁盘文件。

## 7.4 系统框图与流程图要点

- **系统框图（4.2.1）与流程图（4.2.3）**均仅用 **fenced mermaid**（`mermaid_render.py` 经 **Playwright + 内置 `tools/vendor/mermaid.min.js`** 出 PNG，与查新共用 `tools/browser.py`：系统 Chrome → Edge → 自带 Chromium；**不依赖** Node / mmdc / npx / 外网 PlantUML）；Word 中以 PNG 为准，**无需**再附 ASCII 文字框图
- mermaid 内节点标签用**简短中文/数字**的**场景领域词**，避免 ①②③；实现细节（校验值、序号、字段名等）放正文，不要堆进节点标签。**用标题里的领域对象**命名节点，**不要**换成更空的上位词（见 §7.9）。可另写简短「流程说明」段落概括各步，**不得**用 ASCII 框线箭头代替图示
- **步骤号必须写进可见标签**：节点 id（`S1`）**不会**出现在 PNG 上。正确：`S1["S1 采集节点指标"]`、`S5{"S5 是否达阈"}`；错误：`S1[采集节点指标]`（出图只剩中文、序号丢失）。定稿时 `mermaid_render.py` 会把缺失序号补进标签再出图；成文时仍须按正确写法写，勿依赖脚本补救
- 第六章「附图及说明」须**汇总**第四章已渲染的附图（图号 + 图名 + 来源章节），并做简要说明

## 7.5 脱敏 / 模糊化要求（对齐 docx「模糊化处理」）

docx 模板允许并鼓励对**不便公开的部分做模糊化处理**（用户在文中标注后，由代理人统一权衡）。本技能面向**所内正式交底**，默认保留真实信息；用户明示需保护的项按表处理并在文中**就地标注「【建议模糊化】」**，**不擅自删改技术事实**。完整对照表见 `template_reference.md`「脱敏 / 模糊化检查表」。

| 类型 | 默认 | 需保护时 |
|------|------|----------|
| 业务/行业 | 保留真实 | 抽象为通用描述 + 标注 |
| 具体分类 | 保留真实 | 分类A/B/C + 标注 |
| 具体数值 | 保留真实（写进 4.2.5） | 范围/示例值 + 标注「不作为权利要求限制」 |
| 公司/产品 | 保留真实 | 删除或「某系统」+ 标注 |
| 身份证号/组织机构代码/委托编号 | **始终** `[待填写]` | 不由 Agent 填 |

**图片脱敏（多模态）**：入文或随材料交付的**截图/照片**可能含公司名、产品名、内部代号或敏感数值时，先委派 `multimodal-vision` 子智能体识别图中文字与标识（给图片路径 + 「识别图中公司名/产品名/版本号/数值并逐项列出」），再按上表决定模糊化处理。

**模糊化边界（勿误抽）**：上表挡住的是真实主体、产品名、内部代号和不宜公开的精确数值。**不得**借模糊化把**案件名称中的领域对象**收成更空的上位词（标题有「资源画像」则勿改成「节点数据」；标题有「数字员工」则勿改成「岗位集群」）。实施例中的角色名、工具类别、交付物类型从本案材料归纳，**要具体**，只去掉公司名与真实数据。术语与标题贯穿见 **§7.9**。

## 7.7 符号与公式体例（必遵）

撰写 **4.2.4**、**4.2.5** 及全文含 LaTeX 的段落时须遵循；正/反例与符号表示例见 **`template_reference.md` §4.2.4**。  
范式菜单（可外挂扩展）：**`references/formulas/paradigms.yaml`**（说明见同目录 `README.md`）。

### 成文前：`formula_plan`（有公式时必做）

1. **`Read`** `references/formulas/paradigms.yaml`（或先 `python tools/formula_paradigms.py list` 看清单）。
2. 在案件目录写出 **`formula_plan.yaml`**（合同：`references/schemas/formula_plan.schema.yaml`）：选定 `paradigm_ids` / 可选 `combo_id`、主式人话、本案符号、**可代入数值例**。
3. 校验：`python tools/check_formula_plan.py -i …/formula_plan.yaml --eval`；**不通过不得写 4.2.4**。简单式由脚本代入 `numeric_example` 核对；求和/范数/分位等复杂式脚本会警告跳过，须手算。
4. 再写正文 4.2.4：只展开计划中的式；打分与限频触发宜分式 (1)/(2)。
5. 建议顺序：**流程文字 → 数值走查（可放第五章草稿）→ 锁定公式 → 回填符号表 / 4.2.5**。

覆盖范式：环境变量 `PATENT_FORMULA_PARADIGMS`，或案件目录 `formula_paradigms.yaml`。

### 符号表先行

- 撰写 **4.2.4** 或全文含 LaTeX 时，**先写符号与变量定义**（可按（1）任务/对象下标、（2）节点/环境下标、（3）标量与向量分组），每项至少含：**符号、含义、下标含义（如 \(i\)=任务、\(j\)=节点）、量纲或取值范围**。
- 其后公式、**4.2.5 参数表**、**第五章实施例**中出现的符号须与符号表 **同形、同义**。
- **禁止同一字母多义**：例如任务侧权重用 \(b\)，节点侧饱和度应改用 \(g\)、\(h\) 等其它字母，勿任务/节点共用 \(b\) 表示不同物理量。
- **选题不创作**：主式须来自范式库 `id`（见上文 `formula_plan`）；禁止未登记的装饰性「论文风」自创式。平滑用范式 `ema_smooth` + 独立符号 \(A\)，**禁止** `\tilde`/`\hat`/`\bar` 等装饰音（与范式库 `rules.forbid_accents` 一致）。

### 下标与上标

- **资源维度/类型标签**（cpu、mem、io、peak 等）一律写入 **下标**，维度名用 `\mathrm{cpu}`、`\mathrm{mem}` 等正体，例如 `b_{i,\mathrm{cpu}}`、`a_{j,\mathrm{mem}}`。
- **禁止**用 `^{cpu}`、`^{mem}`、`^{io}` 等 **上标** 表示维度或字段名（易被读作幂次，亦不符合专利正文常见写法）。
- **上标仅用于**：幂次、转置、序号、撇号类标记；**下标用于**对象编号与维度标签。

### LaTeX 分隔与写法（全文统一）

- **行内公式**：全文统一 **`\(...\)`** 或 **`$...$`** 二选一，**不得混用**。
- **块级公式**：全文统一 **`\[...\]`** 或 **`$$...$$`** 二选一，**不得混用**。
- 比较符优先写 `\leq`、`\geq`（定稿工具可兼容 `\le`/`\ge`，正文仍推荐 `\leq`/`\geq`）。
- 块级公式尽量 **单行写完**；需编号时用 `\tag{1}` 或正文写「式 (1)」，**全文择一**并保持体例一致。
- 逻辑连接词（「且」「或」）优先写在公式 **外** 的中文叙述中；若必须写入公式内，用 `\land`/`\lor`，**避免** `\text{且}` 等复杂文本命令（定稿渲染易失败）。
- **防零除**：用与分母 **同量纲** 的 \(\varepsilon\)；**禁止**在容量类分母上裸写 `max(1, b_{\mathrm{mem}})`。

### 跨节一致

- **4.2.4 符号表**、正文首次定义式、**4.2.5「符号」列**、**第五章实施例** 四处须 **逐字同形**。
- 修改任一处符号时，须同步核对上述各处及 4.2.2/4.2.3 文字叙述中的同名变量，并更新 **`formula_plan.yaml`**。

## 定稿交付：Markdown + Word（必做）

**版本与目录**：凡交付均以 **§7.3 第 5 点**「**案件名 + 时间戳**」落盘，并按 **§7.3 第 6 点 / `prompts/versioned_output.md`** 写入当前 `vN-说明-时间戳/` 版本目录、维护根目录 **`版本索引.md`**。

须**同时**交付：

1. **Markdown**：定稿 `.md` **保留** `` ```mermaid`` 围栏源码，并含 ``<!-- ![图示](…png) -->`` 注释引用（由 `mermaid_render.py` 生成）。
2. **Word**：对上一文件执行 `md_to_docx.py`，或使用一条命令：

`python3 tools/mermaid_render.py -i <含图示的草稿.md> -o "<案件名_YYYYMMDDHHmmss>.md"`（默认在同目录生成**同名** `.docx`；可用 `--docx` 指定路径，`--no-docx` 跳过 Word。Word 失败时见终端提示的手动命令。）

   **公式处理**：`md_to_docx.py` 优先经 **`math_to_omml.py`**（`latex2mathml`）把 LaTeX 转为 Word **原生可编辑 OMML 公式**，失败保留原文；**默认不出公式 PNG、不安装 matplotlib**。Mermaid 图仍由 `mermaid_render.py` 渲染为 PNG 嵌入。

（mermaid 出图：Playwright + 内置 `tools/vendor/mermaid.min.js`，与查新共用 `tools/browser.py`。**禁止**为出图执行 `npm` / `npx` / `playwright install chromium`（除非 `tools/browser.py --probe` 显示本机无 Chrome/Edge 且无自带 Chromium）。无可用浏览器时**仍须交付 .md**（围栏保留）；Word 可生成但框图可能为代码块，告知用户补浏览器后可重跑本脚本。依赖见根目录 `requirements.txt`。）

**判读（stderr ≠ 失败）**：以 **退出码 0** 和机读前缀为准：`MERMAID: ok=`、`DOCX: ok=1`、`MATH:`、`omml_text_fallback=`。PowerShell 红字 / `NativeCommandError` / 中文乱码 **不是**失败；**禁止**因此重跑安装或认定 Word 未生成。`DOCX: ok=0` 才按终端里的手动 `md_to_docx.py` 命令补做。

**PNG 读图核对（多模态，渲染成功后）**：对已生成的每张 mermaid PNG，委派 **`multimodal-vision`** 子智能体（Agent 工具，`subagent_type: multimodal-vision`；无则主代理直接读图）逐图核对：S1—Sn 步骤号在**可见标签**内、节点用标题领域词、中文无乱码/缺字、连线与正文一致；发现问题改围栏源码重渲染后再交付（细则见 `disclosure_self_check.md` §8.3「附图 PNG 读图核对」）。

### OMML 失败后的公式 PNG（可选，默认关）

Word 公式主路径为 `latex2mathml` → 可编辑 OMML；失败则 **留 LaTeX 原文**。定稿默认 **不** 预渲染公式 PNG，**禁止**为此自动 `pip install matplotlib`。

若 stderr 出现 `omml_text_fallback=` 或 `OMML_FAIL:` 或 `MATH: ... text=`（`text`>0）：

1. **先完成交付**（仍须写明 `.md` / `.docx` 路径）。
2. 在**本轮回复末尾**反问 **一次**（请回 **是** / **否**），列出失败公式摘要；说明须额外安装 matplotlib（约 100MB，含 numpy 等），图片在 Word 中不可再编辑。

4. 用户回 **是**：本会话最多一次 `pip install matplotlib`（已装则跳过），再对**同一份已定稿 md** 覆盖同名 Word（不必重跑 mermaid）：

   `python3 tools/md_to_docx.py -i "<同名.md>" -o "<同名.docx>" --base-dir "<md 所在目录>" --math-render`

   仍走 OMML 优先；PNG 也画不出的保持原文，**不要再问第二轮**。

脚本禁止 `input()`；反问只在对话里进行。全成功则不问。

## 7.9 场景术语、标题贯穿与实施例（成文必遵）

代理人须能对着本案场景读懂第四章。细则与正/反例见 **`template_reference.md` §4.2.1 / §4.2.3 / 二、所属技术领域 / 第五章**。

### 术语：贴合话题背景（默认就用领域词）

首次成文即用**本案标题与领域场景里能读懂的词**，不要等用户指出后再换。

- **框图 / 步骤标签**：场景短词，且属于本专利话题（以标题为准）。
- **二、所属技术领域及后文**：核心对象和高频过程都用领域可读名。需要把判定方式写清时，用双层：**领域名（如何判定/如何记录）**，括号里也用白话机制，不要把另一领域的行话当正式名称。例：「实际使用资料清单（按实际读过的资料名称与版本登记）」。
- **话题错位检测**：若某词放进标题/领域场景会显得像在写另一技术领域（分布式协议、内容寻址、账本系统等），而本案并不是该领域，则**整篇换成领域表述**，不要靠定义把错位词留下来。指纹、水位、证据账本、幂等标识、媒体锚点等只是**错位词的例子**（随案件而变），**不要**做成禁词表，也**不要**因为「先定义了」就保留。
- **机制仍在**：换成领域词后，仍须能实施（如何判定、如何对齐、如何避免重复执行等）。禁止只换词却说不清判定；也禁止为了保留机制而继续用错位行话当正文术语。
- **何时可用实现词**：该词本身就是本案话题（例如发明就是内容校验或水位协议）时，在领域铺垫处定义后使用。判定标准是**是否属于本标题的领域**，不是「技术上是否精确」。
- **禁止**把某一案件的配置机制（例如「岗位技能包」）写成所有标题的必写模块。

### 二、所属技术领域须铺对象与术语（一小段，不另开章）

所内模板要求本章「一句话到一小段」；含场景铺垫时可写成 3–5 句的一小段（细节仍归第四章）：

1. **场景与参与者**：用案件名称里的领域对象称呼执行主体，不要只用「系统/模块」代替。
2. **标题对象如何进入系统**：从**本案材料**归纳该对象如何被配置、调度或进入执行（材料没有则不要编造固定机制）。
3. **高频术语各一句场景定义**：后文将反复出现的**领域词**在本章立住并全文同词。不要为错位行话做定义来「合法化」它。
